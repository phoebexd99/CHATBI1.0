# CHATBI 项目整合、业务价值与 UI 路线

## 项目定位

CHATBI 当前适合定位为：基于公开匿名电商数据的“可解释智能问数与经营分析助手”。它不是一个已经接入生产广告平台和 WMS 的企业 BI 系统，但已经具备从自然语言到指标、SQL、安全校验、数据库结果、洞察和证据展示的完整作品集链路。

没有真实库存和广告 spend 并不会阻止项目继续深入。当前应把业务价值聚焦在 Olist 已经真实提供的经营问题，并把缺失域明确展示为数据边界，而不是用合成数据制造虚假的 ROAS 或库存结论。

## 现有数据可以支撑什么

### 订单经营

Olist 数据可以支撑：

- 商品成交额、有效订单数、商品件数、客单价、购买客户数；
- 按商品、品类、卖家、客户区域和时间的拆分；
- 支付方式、支付金额、运费、订单状态；
- 配送时效、评价分数和低评分订单定位；
- 趋势、环比/同比式周期比较、异常波动和下钻问题。

### 线索漏斗归因

Olist Marketing Funnel 可以支撑一种有边界的“来源侧归因”：

```text
origin / landing_page / lead_type
          ↓
       MQL 线索
          ↓
   closed deal / seller
```

可以回答：哪个来源带来的 MQL 更多、哪个来源的 closed-deal 转化率更高、不同 lead type 的成交表现如何、成交卖家后续订单表现如何。

这里的“归因”是 MQL 来源到 closed deal 的漏斗归因，不是广告曝光到订单的因果归因，也不是带 spend 的 ROAS。公开数据没有媒体成本、曝光点击链路、订单级 campaign_id、退款和利润字段，因此页面和回答中应使用“线索来源转化率”“来源侧成交表现”等名称。

### 智能问数

当前已经可以展示一条完整的可解释路径：

```text
用户问题
  → 意图与指标识别
  → 指标目录 / 业务术语 / Verified SQL 检索
  → LangGraph 节点级 Trace
  → Wren/本地语义适配器生成受控 SQL
  → SQLGlot 只读安全门
  → PostgreSQL Olist Mart 或本地 SQLite
  → 结果表、图表、经营洞察、证据
  → SSE 流式返回前端
```

Live 模式使用 FastAPI → LangGraph → RAG/Wren 适配器 → SQL 安全门 → PostgreSQL；GitHub Pages Replay 使用静态 fixture 重放同样的产品状态，不依赖后端和数据库。

## 页面 UI 优化思路

### 1. 问数工作台 `/`

目标是让用户先看到“结论是否可信”，再查看过程细节。

建议布局：

```text
问题输入 / 示例问题
        ↓
状态条：理解中 → 检索中 → 生成 SQL → 安全校验 → 执行完成
        ↓
经营结论 + 关键数值 + 环比变化
        ↓
图表 / 结果明细 / 可追问建议
        ↓
证据抽屉：指标口径、命中知识、SQL、Trace、数据来源
```

优先优化：

- 将“数据集：Olist、时间范围、指标版本”放在结论卡片顶部；
- 把“线索来源转化率”与“广告 ROAS”做明显区分，并在归因问题旁展示口径提示；
- 图表增加空值、样本量、时间范围和币种信息；
- Trace 默认折叠，失败时自动展开失败节点和修复建议；
- 结论下方提供“按品类拆分”“查看口径”“追问原因”等下一步动作；
- Replay/Live 模式使用同一套视觉状态，只在状态条标识数据来源。

### 2. 知识中心 `/knowledge`

目标是让知识中心成为“指标合同和证据浏览器”，而不是静态文档列表。

建议增加：

- 按知识类型筛选：指标、数据集、字段、业务术语、Verified SQL；
- 指标卡展示公式、时间字段、允许维度、负责人、版本、审核状态；
- 证据详情展示“该知识被哪些评测用例引用”；
- 显示 Olist 数据边界，例如“无库存快照”“无广告 spend”“无退款流水”；
- 为每条指标提供“用这个指标提问”按钮，直接带入问数工作台；
- 增加来源标签：公开数据、业务规则、Verified SQL、设计约束。

### 3. 评测中心 `/evaluations`

目标是把评测从“题目列表”升级成质量控制台。

建议增加：

- 顶部展示执行准确率、澄清成功率、安全拒答率、证据命中率、平均延迟；
- 按指标问数、知识问答、归因分析、边界拒答、失败修复筛选；
- 每个用例详情并排展示问题、期望语义、实际 SQL、命中证据、Trace 和失败原因；
- 明确区分开发 Golden、发布 Holdout 和未来真实业务题；
- 增加“数据 profile”字段，避免 Olist、demo、未来 TheLook 的题目混在一起；
- 用例失败时提供“新增 Verified SQL / 修改指标口径 / 需要澄清”的归因分类。

## 当前项目的价值边界

| 能力 | 当前状态 | 可以如何表达 |
| --- | --- | --- |
| 订单经营问数 | 可用 | 基于 Olist Mart 的认证订单分析 |
| 线索来源转化 | 可用但有限定 | MQL → closed deal 的来源侧漏斗归因 |
| 广告 ROAS | 不可认证 | 缺 spend、归因窗口和订单级媒体键 |
| 实际库存 | 不可认证 | Olist 没有 WMS/ERP on-hand 快照 |
| 智能 SQL | 作品集可用 | 受指标目录、检索和安全门约束的 SQL 生成 |
| 因果归因 / 增量效果 | 不可认证 | 缺实验组、曝光链路和统一归因键 |
| 生产级权限 | 尚未完成 | 后续接入认证、RLS、PII 策略和审计 |

## 推荐实施顺序

### P0：现在即可完成

1. 将 Olist 设为默认的公开数据 profile，并在 UI 明示数据集与边界；
2. 增加来源侧漏斗归因问题模板和 Verified SQL；
3. 将“口径、证据、SQL、Trace”统一收纳到结果详情抽屉；
4. 为 45 条开发题补齐归因、趋势、根因下钻和拒答场景；
5. 继续保留 GitHub Pages Replay，作为无需云端环境的作品集演示入口。

### P1：基于现有 Olist 深挖

1. 增加 cohort、复购、RFM、卖家分层和履约异常分析；
2. 增加订单状态、配送时效、低评分和品类结构的多步追问；
3. 将常见业务问题沉淀为指标版本、口径说明和 Verified SQL；
4. 引入模型做实体抽取、复杂问题拆解和自然语言解释，但 SQL 仍必须经过安全门。

### P2：有资料后再接入

1. 脱敏 WMS/ERP 日快照 → 库存、缺货、周转和补货指标；
2. 广告平台日汇总 → spend、点击、转化、归因收入和 ROAS；
3. 统一 SKU、渠道、活动和日期键后，再做跨域归因；
4. 通过 pgvector 检索指标规则、数据字典和历史 Verified SQL。

### P3：生产化

认证与 RLS、PII 分级、指标审核/下线、生产 Wren、OpenTelemetry、查询配额、缓存、告警和云端应用部署。

## 验收标准

在没有真实库存和广告数据的前提下，项目仍可以用以下标准证明完成度：

- Olist 订单核心问题可执行、可解释、可追溯；
- 来源侧漏斗归因明确展示 MQL、closed deal 和观察窗口；
- 每次回答都有指标口径、证据、SQL 安全结果和 Trace；
- 无法支持的 ROAS、库存和因果结论会澄清或拒答；
- Replay 与 Live 的状态和结果结构一致；
- Golden 回归、失败场景和安全边界持续通过测试。
